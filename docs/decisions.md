# Decisions

1. **New code, same data (2026-11-11).** The engine runs against the existing database while the old system keeps running. Features move one screen or job at a time. This repo applies no schema changes until the old system has stopped applying its own, so the database never has two owners.

2. **Public repo in the organization (2026-11-11).** Public gives us the merge queue and free CI minutes. The cost is that nothing real about the business may appear here, which is why tests use made-up data.

3. **GitHub is the engineering dashboard (2026-11-11).** Issues, pull requests and a Projects board track all work. Work is not tracked in the database.

4. **One check (2026-11-11).** Pull requests and the merge queue run the identical command, `npm run check`, with no secrets and no network, capped at 5 minutes. A change that passes on its pull request cannot meet a different test in the queue.

5. **Stack (2026-11-11).** TypeScript on one Cloudflare Worker with Hono for routing. Node's built-in test runner, so tests need no framework. Biome for lint and format, knip to fail the check on unused code, `tsc` for types.

6. **Reuse browser sessions (2026-11-11).** The engine validates the existing host-only session cookie through CARR’s `/auth/session`, preserving the browser origin and host. CARR remains responsible for session storage and renewal until sign-in moves in a later issue. Engine writes always require the returned CSRF token, same-origin Origin and fetch metadata. Authentication outages fail closed with 503. Node compatibility enables the platform’s native `timingSafeEqual` on SHA-256 token digests, so unequal token lengths also receive a constant-time comparison without a new dependency.

7. **Real SQL in disposable PostgreSQL (2026-11-11).** Use the GitHub Actions PostgreSQL 18 service and the same server version locally. Both PostgreSQL 18.6 and PGlite 0.5.16 loaded the reviewed business snapshot with pgcrypto and pg_trgm in five alternating runs. Restore medians were 0.269 seconds for PostgreSQL and 0.805 seconds for PGlite, with ranges of 0.205–0.408 and 0.671–1.243 seconds. PGlite includes instance startup; PostgreSQL excludes cluster provisioning, which Actions owns. Both fit the budget, so the existing platform feature wins. Each check creates and drops its own database and generates Kysely types from its restored catalog before TypeScript runs. The separate drift command reads only the target catalog and compares selected objects. It ignores a quoted value only where the snapshot holds one of the made-up values in `schema/made-up-literals.json` that replaced a real one, so privacy scrubbing does not report drift and any other changed value does (#50). The snapshot includes only public structure and constraints and its public-function triggers. Side effects of old CARR's triggers on writes are checked by the old-versus-new comparison (#6) against staging, not here. The engine never applies this snapshot to the shared database.

8. **Deploy on merge (2026-11-11).** Every push to main deploys staging, then production, with Wrangler's version commands. For each Worker the workflow uploads a version without traffic, checks `/health` on that version's preview URL, promotes it to 100%, and checks `/health` on the live URL. Each check passes only when `/health` reports the uploaded version ID. Cloudflare can briefly answer that a version it just uploaded cannot be found (code 100146), so the promotion retries that same version every 10 seconds, six tries in all, and rolls back at once on any other error (#172). A failed live check rolls back to the version that was live before, and any failure opens an issue. The Cloudflare token can deploy any Worker in the account, so it and the account ID are secrets of the `production` environment, which only main can use, and the workflow names `doctorcre-engine` and `doctorcre-engine-staging` itself. A plain `wrangler deploy` runs only when Wrangler reports that the Worker is missing or has no deployments, because version uploads need an existing Worker with preview URLs on. Any other failure to read the live version stops the run before it deploys anything. Version uploads do not apply triggers, so a change to routes or `workers_dev` needs `wrangler triggers deploy`.

9. **Reading the business database (2026-11-11).** The Worker reaches the database through Cloudflare Hyperdrive with the `pg` driver and Kysely's PostgreSQL dialect, so tests run the same driver as production. Its Hyperdrive config has query caching off (`wrangler hyperdrive create … --caching-disabled`), because cached reads would show stale boards after writes made through the old system. Every answer runs inside one `REPEATABLE READ READ ONLY` transaction, so it reads one snapshot. The cost is that each answer holds one pooled Hyperdrive connection until it finishes, where single queries would hand the connection back between statements. The transaction's first statement is a query that sets the zone to UTC, which also takes the snapshot, so a caller can no longer switch the transaction to read write. A caller that issues `commit` can still leave the transaction. The login's own read-only default and its grants are the real guard. Numeric and bigint come back as strings. Every date, timestamp and timestamptz, and numeric, date and timestamp arrays, come back as the text PostgreSQL sends, as strings or arrays of strings. JavaScript Dates would drop microseconds and shift with the machine's zone, and floats would lose digits. The generated types say `string` for these. The capture queue casts its confidence to float8 in SQL, as the old system did, so it prints as a JSON number. The engine sets UTC itself rather than relying on any server default, because Hyperdrive resets session settings between transactions. The login holds SELECT on `activity`, `actor`, `board_snapshot`, `client`, `client_status`, `client_type`, `commission`, `deal`, `doctrine_section`, `lead`, `next_action`, `party`, `party_link`, `party_link_deal`, `practice_origination_event`, `practice_origination_feed`, `vendor`, `vendor_category`, `vendor_disposition`, `vendor_market`, `vendor_market_key`, `vendor_market_membership`, `vendor_market_regional_reference`, `vendor_relationship_level`, `vendor_stage` and the views the board, deal, change feed, capture queue, search, lead board, opened lead, quiet follow-ups, territory, reasons to reach out, client list, vendor track record, vendor markets, recent activity, invoices, today's meetings, suggested vendor meetings and today's reminders reads name, and execute on `practice_address_key(text)`, and nothing else. As of 2026-11-13 the production login holds every grant listed here. The client list and client detail read `client_status` and `client_type` too. The vendor track record reads `activity`, `party_link` and `party_link_deal` too, and the vendor list the four vendor lookups. Vendor markets read the four `vendor_market` tables, `v_vendor_assignment_context` and `v_record_flag_subject`, and the vendor list and a vendor's details under `vendor-directory.v2` read the last two for the vendor's people. The Relationships map reads `actor`, `client`, `deal`, `lead`, `party`, `party_link`, `party_link_deal` and `vendor`. Recent activity reads a partner's calendar captures through `v_calendar_capture_receipt`, where the old system read `tool_call` on its writer login. The old system's migration 1185 creates that view and grants it, and the login holds no grant on `tool_call`. Recent activity also reads `v_subject_timeline` and search's `v_party_graph` and `v_lead_client_best`. Today's meetings read the partner's Outlook snapshot from `board_snapshot`, their attendees' open deals through `v_export_clients` and `v_export_deals`, and those deals' preparation from `v_open_deal_room_board`. Each read that fails, such as one without a grant, answers in part as the old system did, and its savepoint keeps the transaction able to commit. Suggested vendor meetings read the vendor's people through `v_vendor_assignment_context`, `party` and `v_record_flag_subject`, check holds on `party`, `vendor` and `lead`, and read the partner's snapshot from `board_snapshot`. Today's reminders read `v_today_triage`, which calls `carr_business_date()` and `carr_business_days(date, date)`, on which the login holds execute. The client fit reads `deal`, `client` and `party` directly, as the old system did. Those views read their tables with their owner's rights. The checklist reads `commission` itself because the production login has no grant on `v_deal_room_commission`. The checklist and quiet follow-ups call `carr_business_date()`. The board, deal detail, search, lead board, opened lead and connection check call it through `v_last_touch`, and PostgreSQL checks execute on a function inside a view against the login running the query, not the view's owner. Production revoked PUBLIC's execute on that function and on `practice_address_key(text)`, so the login holds its own grants. A test runs the reads as a login holding only these grants. Staging has its own Hyperdrive binding under `env.staging`, on the engine-test database (#41).

10. **A feature moves when three things are true (2026-11-11, revised 2026-11-12).** Someone used it in the last 30 days, and it is business, not build process (#2). Its reads move first. The Deals board's writes stay on the old system until its read has run in production (#17). The engine's answers matched the old system's on real requests (#6). The Deals board and deal detail moved first (#17), and the owner judged the read pattern proven (#87), so reads of later screens may start before Deals is done. Saves still move one screen at a time. Until a feature moves, the old system keeps serving it, and since 2026-11-11 it takes only fixes and engine requests.

11. **Only the owner changes the rules (2026-11-11).** `.github/CODEOWNERS` gives the owner `AGENTS.md`, `CLAUDE.md` and `.github/`, the files that say how agents work and what the check and deploys run. Every other file, `package.json`, `README.md`, `docs/`, `scripts/` and `schema/` included, is merged by agents as usual. The ruleset requires code-owner review, so a pull request that changes an owned file cannot merge by itself. The old system grew because any agent could add a rule, a gate or a workflow while doing something else. Here that takes the owner's click. Agents and the owner share one GitHub login today, so no one can approve such a pull request, and the owner merges it with a bypass from the pull request page. A bypass also skips the check. A separate login for agents would make this a normal approval.

12. **Saves keep the old history and retry rules (2026-11-12).** Every engine save runs through `runSave` in `src/save.ts`: one READ COMMITTED transaction that resolves the partner's `actor` row, locks the retry key with the old system's lock text, replays a `tool_call` answer from the last 30 days, and writes `event` rows and the `tool_call` receipt with the old system's columns and values for a partner in the app. The request hash is the engine's own (`doctorcre-engine-save.v1`), because the old hash includes a registry digest that changes with each old release; a retry that crosses a save's switch is refused once as `key_reuse`. The engine sets none of the old `carr.*` transaction settings, because no trigger or function on the save path reads them (#41).

13. **Search picks one order where the old one had none (2026-11-12).** The old `find` read left ties unordered: parties and organizations by similarity, connections after their time and names, and the five deals it returns with no order at all. The engine breaks each tie the same way every time: parties by ref, then kind; organizations by name; deals by name, then id; connections by from_ref, to_ref, kind and note; lead-to-client links by lead id; linked deals by id. Where the old answer was arbitrary, a comparison must treat those rows as unordered, and a full list of five deals as one of several right answers. The trigram match uses pg_trgm's default similarity threshold of 0.3, which no role or database setting in production changes, so the engine sets none.

14. **Refusals keep the old bodies, with these exceptions (2026-11-12).** A missing sign-in answers the old browser door's `{"error":"unauthorized","state":"sign_in_required"}` even with no cookie at all, where the old `/mcp` and `/pipeline/changes` handed a cookie-less request to their OAuth door, which the engine does not have. On the client and vendor lists and details and the Relationships map it answers that body where the old door answered 401 `{"error":"AUTHENTICATION_REQUIRED"}`, and under `/api/engine/` it answers before it checks the path, so any address there it does not serve, such as a client or vendor id that is not a UUID, a percent-encoded address or an unknown path, gets 401 where the old door answered an unserved `/api/v1/` address 404 `not_found` before sign-in. Outside `/api/engine/`, an address it does not serve gets 404 `not_found`, signed in or not. The old Clients page signs out on any 401, whatever its body. A sign-in outage answers the old Worker's `internal_error` body at 503, not its 500 (decision 6). A non-GET request without the write proofs is refused 403 before any route runs, so a POST to the change feed gets 403 where the old feed answered 405 (decision 6). A refused or failed read the old system served as a tool answers an HTTP error status, such as 500 for a failed read, where the old `/mcp` answered 200 with the error inside its JSON-RPC envelope. Any method but GET or HEAD that carries the write proofs gets 404 `{"error":"not_found"}` at a read's address other than the change feed. Of those reads, only the client and vendor lists and details and the Relationships map had an old address of their own, where the old door answered 204 to OPTIONS and 405 `METHOD_NOT_ALLOWED` to any other method; every other read it ports the old system served only through `/mcp`. A save whose body is JSON but not an object, such as `[]` or `null`, answers `{"error":"invalid_json"}`, where the old door answered `missing_required` naming every required field. A save checks its input, including its `idempotency_key`, before it resolves the partner's `actor` row, where the old door resolved it first, so a partner with no actor row who also sends a bad request gets the input refusal instead of `actor_not_provisioned` (decision 18). Only saves answer with an `x-correlation-id` header and honor the caller's; a read answers without one and puts a fresh id in each refusal, where the old Worker used one id per request on every response. A repeated query field stands for the old input's list: it gets the old refusal wherever the old gate or read refused a list, but where the old read carried the list on to the database, the engine reads the first value.

15. **The engine carries the old source list (2026-11-12).** Reasons to reach out spreads each configured source into its coverage answer, and the old system kept that list in `mcp-server/src/origination-sources.json`, outside the database. The engine keeps it as a typed constant in `src/leads/origination-sources.ts`, in the old key order, not as a table, because decision 1 bars schema changes. Until the old system stops importing, a change to its file must be copied there, or the coverage answers differ.

16. **A vendor's track record picks one order where the old one had none (2026-11-12).** The old track record listed a vendor's introductions by when they were recorded, and its twenty recent entries by when they happened, with no tie-break. The engine breaks both ties by id, highest first, the order the old read already used to choose the twenty. A comparison must treat tied rows as unordered.

17. **Recent activity picks one order where the old one had none (2026-11-12).** The old `find-and-catch-up` timeline sorted by `occurred_at` alone, so rows at the same moment came back in no set order, and a page could end inside such a tie. The engine breaks the tie by `entry_kind`, then row id. A comparison must treat rows sharing an `occurred_at` as unordered, and a page cut inside a tie as one of several right answers. Finding the record reuses search's order (decision 13).

18. **Saves use their own login and answer like reads (2026-11-12).** A save reaches the database through a second Hyperdrive binding, `DATABASE_WRITER`, which holds the engine's write login with caching off. Only `env.staging` declares it, on engine-test, until the production write login exists, so a save answers 503 `unhandled_verb_failure` in production. A save answers 200 with its answer, or with the old public refusal body and an HTTP error status, as reads do (decision 14). Each save declares its fields to `answerSave` as the old schema did, in the old order: allowed values, booleans, numbers, nullable fields and nested objects (`src/save-door.ts`). It runs the old door's checks on the JSON values in the old order and hands the change and the request hash `"true"` and `"5"` as their types. A save with an array field must first teach the door the old array rules. A save answers a timestamp the old driver read from the database as a JavaScript Date, built from the `isoMillis` text, and every other value as itself, because the old receipt of a long answer dropped a Date and kept a string. `answerSave` uses one correlation id for the answer, its receipt and its failure log, and turns a statement PostgreSQL refuses into the old public refusal. The old system named a field (`invalid_field_value`) only when PostgreSQL named a column that is a declared field at any depth, as for a not-null violation, and otherwise answered `database_refused_the_statement`, because its driver returned the catalog's column list as unparsed text. The old schema reads the `carr.*` transaction settings in 78 places, so each later save lists what the triggers, functions and row policies on its tables read before it moves; presence's two tables read none. The presence ping needs two grants beyond the old job's inventory on #41: INSERT on `deal_presence_lease` and UPDATE of its `expires_at`, which that inventory names as the ping's own addition, and SELECT on `tool_call`'s `idempotency_key`, `request_hash`, `response` and `created_at`, which every save needs to replay an answer. A test runs the ping as a login holding only those grants.

19. **Invoices pick one order where the old one had none (2026-11-12).** The old `read-invoice-tracker` sorted by deal name, commission invoiced date and commission id, so two same-name deals without a commission came back in no set order. The engine breaks that tie by deal id. A comparison must treat rows tied on those three keys as unordered.

20. **People and companies stay one list (2026-11-13).** The new database keeps every person and company in `party`, with `kind` saying which, rather than separate tables for people and companies, so a deal's people, a role and a round's sender each point at either kind with one key. A person's place at a company is a dated `party_company` row with their title, start date and end date. People change companies, so a move ends the old row and adds a new one, and their history at the old company survives (#196).

21. **"About" links are checked keys (2026-11-13).** In the new database, a row that may concern a deal, a party or a property, such as `activity_about` and `next_step`, holds one nullable foreign key per kind and a check that exactly one is set. A type word beside a bare id would let the row name a record that does not exist or was removed. A new kind of record is one more column and one more name in the check (#199).

22. **Only emails about a record are stored (2026-11-13).** The database refuses an email about no record, so it grows with deal work, not with mailbox traffic (#199).

23. **Not measured is a reason, never a zero (2026-11-13).** In the new database, a marketing reading that could not be taken is stored with a reason and no value, and a row with both or neither is refused. Ratios such as engagement per view are calculated when read. A read leaves out a post that is missing a number it needs, rather than counting the gap as zero (#204).

24. **Posts are compared at day 7 (2026-11-13).** A post's numbers grow for days, so `posts_at_day_7` judges each post by its latest reading at or before 168 hours after publishing, and only once it is that old. The cut is in hours, not days, so a clock change cannot move it (#204). A post must have every metric its platform reports, from the `platform_metric` rows, so a platform that reports no saves still compares. Each ranked post shows the age of its oldest reading, rather than the read setting a minimum.
