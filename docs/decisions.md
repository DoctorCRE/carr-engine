# Decisions

1. **New code, same data (2026-11-11).** The engine runs against the existing database while the old system keeps running. Features move one screen or job at a time. This repo applies no schema changes until the old system has stopped applying its own, so the database never has two owners.

2. **Public repo in the organization (2026-11-11).** Public gives us the merge queue and free CI minutes. The cost is that nothing real about the business may appear here, which is why tests use made-up data.

3. **GitHub is the engineering dashboard (2026-11-11).** Issues, pull requests and a Projects board track all work. Work is not tracked in the database.

4. **One check (2026-11-11).** Pull requests and the merge queue run the identical command, `npm run check`, with no secrets and no network, capped at 5 minutes. A change that passes on its pull request cannot meet a different test in the queue.

5. **Stack (2026-11-11).** TypeScript on one Cloudflare Worker with Hono for routing. Node's built-in test runner, so tests need no framework. Biome for lint and format, knip to fail the check on unused code, `tsc` for types.

6. **Reuse browser sessions (2026-11-11).** The engine validates the existing host-only session cookie through CARR’s `/auth/session`, preserving the browser origin and host. CARR remains responsible for session storage and renewal until sign-in moves in a later issue. Engine writes always require the returned CSRF token, same-origin Origin and fetch metadata. Authentication outages fail closed with 503. Node compatibility enables the platform’s native `timingSafeEqual` on SHA-256 token digests, so unequal token lengths also receive a constant-time comparison without a new dependency.

7. **Real SQL in disposable PostgreSQL (2026-11-11).** Use the GitHub Actions PostgreSQL 18 service and the same server version locally. Both PostgreSQL 18.6 and PGlite 0.5.16 loaded the reviewed business snapshot with pgcrypto and pg_trgm in five alternating runs. Restore medians were 0.269 seconds for PostgreSQL and 0.805 seconds for PGlite, with ranges of 0.205–0.408 and 0.671–1.243 seconds. PGlite includes instance startup; PostgreSQL excludes cluster provisioning, which Actions owns. Both fit the budget, so the existing platform feature wins. Each check creates and drops its own database and generates Kysely types from its restored catalog before TypeScript runs. The separate drift command reads only the target catalog and compares selected objects, normalizing quoted SQL string literals on both sides so privacy scrubbing does not report drift. The snapshot includes only public structure and constraints and its public-function triggers. Side effects of old CARR's triggers on writes are checked by the old-versus-new comparison (#6) against staging, not here. The engine never applies this snapshot to the shared database.

8. **Deploy on merge (2026-11-11).** Every push to main deploys staging, then production, with Wrangler's version commands. For each Worker the workflow uploads a version without traffic, checks `/health` on that version's preview URL, promotes it to 100%, and checks `/health` on the live URL. Each check passes only when `/health` reports the uploaded version ID. A failed live check rolls back to the version that was live before, and any failure opens an issue. The Cloudflare token can deploy any Worker in the account, so it and the account ID are secrets of the `production` environment, which only main can use, and the workflow names `doctorcre-engine` and `doctorcre-engine-staging` itself. A plain `wrangler deploy` runs only when Wrangler reports that the Worker is missing or has no deployments, because version uploads need an existing Worker with preview URLs on. Any other failure to read the live version stops the run before it deploys anything. Version uploads do not apply triggers, so a change to routes or `workers_dev` needs `wrangler triggers deploy`.

9. **Reading the business database (2026-11-11).** The Worker reaches the database through Cloudflare Hyperdrive with the `pg` driver and Kysely's PostgreSQL dialect, so tests run the same driver as production. Its Hyperdrive config has query caching off (`wrangler hyperdrive create … --caching-disabled`), because cached reads would show stale boards after writes made through the old system. Every answer runs inside one `REPEATABLE READ READ ONLY` transaction, so it reads one snapshot. The cost is that each answer holds one pooled Hyperdrive connection until it finishes, where single queries would hand the connection back between statements. The transaction's first statement is a query that sets the zone to UTC, which also takes the snapshot, so a caller can no longer switch the transaction to read write. A caller that issues `commit` can still leave the transaction. The login's own read-only default and its grants are the real guard. Numeric and bigint come back as strings. Every date, timestamp and timestamptz, and numeric, date and timestamp arrays, come back as the text PostgreSQL sends, as strings or arrays of strings. JavaScript Dates would drop microseconds and shift with the machine's zone, and floats would lose digits. The generated types say `string` for these. The capture queue casts its confidence to float8 in SQL, as the old system did, so it prints as a JSON number. The engine sets UTC itself rather than relying on any server default, because Hyperdrive resets session settings between transactions. The login holds SELECT on `activity`, `actor`, `client`, `client_status`, `client_type`, `commission`, `deal`, `doctrine_section`, `lead`, `next_action`, `party`, `party_link`, `party_link_deal`, `practice_origination_event`, `practice_origination_feed`, `vendor`, `vendor_category`, `vendor_disposition`, `vendor_relationship_level`, `vendor_stage` and the views the board, deal, change feed, capture queue, search, lead board, opened lead, quiet follow-ups, territory, reasons to reach out, client list, vendor track record and recent activity reads name, and execute on `practice_address_key(text)`, and nothing else. The production login already held the four the quiet follow-ups added. Production lacks `v_party_graph`, `v_lead_client_best`, `v_lead_workspace`, `v_lead_prospect_engagement`, `v_lead_workspace_correspondence`, `v_lead_workspace_stage_history` and `v_record_flag_subject` until the owner grants them, so search, the lead board, an opened lead and territory fail there until then. Production also lacks `practice_origination_event`, `practice_origination_feed`, `v_practice_origination_party_address` and execute on `practice_address_key(text)`, whose PUBLIC execute it revoked, so reasons to reach out and the lead board fail there until the owner grants them. The client list and client detail read `client_status` and `client_type` too, which the production login already held. The vendor track record reads `activity`, `party_link` and `party_link_deal` too, and the vendor list the four vendor lookups, which the production login already held. Recent activity reads a partner's calendar captures through `v_calendar_capture_receipt`, where the old system read `tool_call` on its writer login. The old system's migration 1185 creates that view and grants it, and the login holds no grant on `tool_call`. Production lacks `v_calendar_capture_receipt` until that migration runs and lacks `v_subject_timeline` until the owner grants it, and recent activity also needs search's `v_party_graph` and `v_lead_client_best`, so it fails there until then. The client fit reads `deal`, `client` and `party` directly, as the old system did, and the production login already held those grants. Those views read their tables with their owner's rights. The checklist reads `commission` itself because the production login has no grant on `v_deal_room_commission`. The checklist and quiet follow-ups call `carr_business_date()`. The board, deal detail, search, lead board, opened lead and connection check call it through `v_last_touch`, and PostgreSQL checks execute on a function inside a view against the login running the query, not the view's owner. Production revoked PUBLIC's execute on that function, so the login holds its own grant. A test runs the reads as a login holding only these grants. Staging needs its own Hyperdrive binding under `env.staging`.

10. **A feature moves when three things are true (2026-11-11).** Someone used it in the last 30 days, and it is business, not build process (#2). Its reads move first. The Deals board's writes stay on the old system until its read has run in production (#17). The engine's answers matched the old system's on real requests (#6). The Deals board and deal detail move first (#17). One screen goes end to end before a second starts, because the first sets the pattern the rest copy. Until a feature moves, the old system keeps serving it and keeps taking business features and fixes.

11. **Only the owner changes the rules (2026-11-11).** `.github/CODEOWNERS` gives the owner `AGENTS.md`, `CLAUDE.md` and `.github/`, the files that say how agents work and what the check and deploys run. Every other file, `package.json`, `README.md`, `docs/`, `scripts/` and `schema/` included, is merged by agents as usual. The ruleset requires code-owner review, so a pull request that changes an owned file cannot merge by itself. The old system grew because any agent could add a rule, a gate or a workflow while doing something else. Here that takes the owner's click. Agents and the owner share one GitHub login today, so no one can approve such a pull request, and the owner merges it with a bypass from the pull request page. A bypass also skips the check. A separate login for agents would make this a normal approval.

12. **Saves keep the old history and retry rules (2026-11-12).** Every engine save runs through `runSave` in `src/save.ts`: one READ COMMITTED transaction that resolves the partner's `actor` row, locks the retry key with the old system's lock text, replays a `tool_call` answer from the last 30 days, and writes `event` rows and the `tool_call` receipt with the old system's columns and values for a partner in the app. The request hash is the engine's own (`doctorcre-engine-save.v1`), because the old hash includes a registry digest that changes with each old release; a retry that crosses a save's switch is refused once as `key_reuse`. The engine sets none of the old `carr.*` transaction settings, because no trigger or function on the save path reads them (#41).

13. **Search picks one order where the old one had none (2026-11-12).** The old `find` read left ties unordered: parties and organizations by similarity, connections after their time and names, and the five deals it returns with no order at all. The engine breaks each tie the same way every time: parties by ref, then kind; organizations by name; deals by name, then id; connections by from_ref, to_ref, kind and note; lead-to-client links by lead id; linked deals by id. Where the old answer was arbitrary, a comparison must treat those rows as unordered, and a full list of five deals as one of several right answers. The trigram match uses pg_trgm's default similarity threshold of 0.3, which no role or database setting in production changes, so the engine sets none.

14. **Refusals keep the old bodies, with seven exceptions (2026-11-12).** A missing sign-in answers the old browser door's `{"error":"unauthorized","state":"sign_in_required"}` even with no cookie at all, where the old `/mcp` and `/pipeline/changes` handed a cookie-less request to their OAuth door, which the engine does not have. On the client and vendor lists and client detail it answers that body where the old door answered 401 `{"error":"AUTHENTICATION_REQUIRED"}`, and it answers before it checks the path, so a client id that is not a UUID gets 401 where the old door answered 404 `not_found`. The old Clients page signs out on any 401, whatever its body. A sign-in outage answers the old Worker's `internal_error` body at 503, not its 500 (decision 6). A non-GET request without the write proofs is refused 403 before any route runs, so a POST to the change feed gets 403 where the old feed answered 405 (decision 6). A refused or failed read the old system served as a tool answers an HTTP error status, such as 500 for a failed read, where the old `/mcp` answered 200 with the error inside its JSON-RPC envelope. A POST or OPTIONS that carries the write proofs gets a plain-text 404, where the old door answered 204 or 405 `METHOD_NOT_ALLOWED`. A reserved field name such as `actor` or `tenant` gets `unregistered_operation_fields`, where the old door answered `caller_authority_field_forbidden` (#137). The app never sends these.

15. **The engine carries the old source list (2026-11-12).** Reasons to reach out spreads each configured source into its coverage answer, and the old system kept that list in `mcp-server/src/origination-sources.json`, outside the database. The engine keeps it as a typed constant in `src/leads/origination-sources.ts`, in the old key order, not as a table, because decision 1 bars schema changes. Until the old system stops importing, a change to its file must be copied there, or the coverage answers differ.

16. **A vendor's track record picks one order where the old one had none (2026-11-12).** The old track record listed a vendor's introductions by when they were recorded, and its twenty recent entries by when they happened, with no tie-break. The engine breaks both ties by id, highest first, the order the old read already used to choose the twenty. A comparison must treat tied rows as unordered.

17. **Recent activity picks one order where the old one had none (2026-11-12).** The old `find-and-catch-up` timeline sorted by `occurred_at` alone, so rows at the same moment came back in no set order, and a page could end inside such a tie. The engine breaks the tie by `entry_kind`, then row id. A comparison must treat rows sharing an `occurred_at` as unordered, and a page cut inside a tie as one of several right answers. Finding the record reuses search's order (decision 13).
