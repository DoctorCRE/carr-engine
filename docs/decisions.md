# Decisions

1. **New code, same data (2026-11-11).** The engine runs against the existing database while the old system keeps running. Features move one screen or job at a time. This repo applies no schema changes until the old system has stopped applying its own, so the database never has two owners.

2. **Public repo in the organization (2026-11-11).** Public gives us the merge queue and free CI minutes. The cost is that nothing real about the business may appear here, which is why tests use made-up data.

3. **GitHub is the engineering dashboard (2026-11-11).** Issues, pull requests and a Projects board track all work. Work is not tracked in the database.

4. **One check (2026-11-11).** Pull requests and the merge queue run the identical command, `npm run check`, with no secrets and no network, capped at 5 minutes. A change that passes on its pull request cannot meet a different test in the queue.

5. **Stack (2026-11-11).** TypeScript on one Cloudflare Worker with Hono for routing. Node's built-in test runner, so tests need no framework. Biome for lint and format, knip to fail the check on unused code, `tsc` for types.

6. **Reuse browser sessions (2026-11-11).** The engine validates the existing host-only session cookie through CARR’s `/auth/session`, preserving the browser origin and host. CARR remains responsible for session storage and renewal until sign-in moves in a later issue. Engine writes always require the returned CSRF token, same-origin Origin and fetch metadata. Authentication outages fail closed with 503. Node compatibility enables the platform’s native `timingSafeEqual` on SHA-256 token digests, so unequal token lengths also receive a constant-time comparison without a new dependency.

7. **Real SQL in disposable PostgreSQL (2026-11-11).** Use the GitHub Actions PostgreSQL 18 service and the same server version locally. Both PostgreSQL 18.6 and PGlite 0.5.16 loaded the reviewed business snapshot with pgcrypto and pg_trgm in five alternating runs. Restore medians were 0.269 seconds for PostgreSQL and 0.805 seconds for PGlite, with ranges of 0.205–0.408 and 0.671–1.243 seconds. PGlite includes instance startup; PostgreSQL excludes cluster provisioning, which Actions owns. Both fit the budget, so the existing platform feature wins. Each check creates and drops its own database and generates Kysely types from its restored catalog before TypeScript runs. The separate drift command reads only the target catalog and compares selected objects, normalizing quoted SQL string literals on both sides so privacy scrubbing does not report drift. The snapshot includes only public structure and constraints and its public-function triggers. Side effects of old CARR's triggers on writes are checked by the old-versus-new comparison (#6) against staging, not here. The engine never applies this snapshot to the shared database.

8. **Deploy on merge (2026-11-11).** Every push to main deploys staging, then production, with Wrangler's version commands. For each Worker the workflow uploads a version without traffic, checks `/health` on that version's preview URL, promotes it to 100%, and checks `/health` on the live URL. Each check passes only when `/health` reports the uploaded version ID. A failed live check rolls back to the version that was live before, and any failure opens an issue. The Cloudflare token can deploy any Worker in the account, so it and the account ID are secrets of the `production` environment, which only main can use, and the workflow names `doctorcre-engine` and `doctorcre-engine-staging` itself. A plain `wrangler deploy` runs only when Wrangler reports that the Worker is missing or has no deployments, because version uploads need an existing Worker with preview URLs on. Any other failure to read the live version stops the run before it deploys anything. Version uploads do not apply triggers, so a change to routes or `workers_dev` needs `wrangler triggers deploy`.

9. **Reading the business database (2026-11-11).** The Worker reaches the database through Cloudflare Hyperdrive with the `pg` driver and Kysely's PostgreSQL dialect, so tests run the same driver as production. Its Hyperdrive config has query caching off (`wrangler hyperdrive create … --caching-disabled`), because cached reads would show stale boards after writes made through the old system. Every answer runs inside one `REPEATABLE READ READ ONLY` transaction, so it reads one snapshot. The cost is that each answer holds one pooled Hyperdrive connection until it finishes, where single queries would hand the connection back between statements. The transaction's first statement is a query that sets the zone to UTC, which also takes the snapshot, so a caller can no longer switch the transaction to read write. A caller that issues `commit` can still leave the transaction. The login's own read-only default and its grants are the real guard. Numeric and bigint come back as strings. Every date, timestamp and timestamptz, and numeric, date and timestamp arrays, come back as the text PostgreSQL sends, as strings or arrays of strings. JavaScript Dates would drop microseconds and shift with the machine's zone, and floats would lose digits. The generated types say `string` for these. The engine sets UTC itself rather than relying on any server default, because Hyperdrive resets session settings between transactions. The login holds SELECT on `actor`, `commission`, `doctrine_section` and the views the board and deal reads name, and nothing else. Those views read their tables with their owner's rights. The checklist reads `commission` itself because the production login has no grant on `v_deal_room_commission`. A test runs both reads as a login holding only that list. Staging needs its own Hyperdrive binding under `env.staging`.

10. **A feature moves when three things are true (2026-11-11).** Someone used it in the last 30 days, and it is business, not build process (#2). Its reads move first. The Deals board's writes stay on the old system until its read has run in production (#17). The engine's answers matched the old system's on real requests (#6). The Deals board and deal detail move first (#17). One screen goes end to end before a second starts, because the first sets the pattern the rest copy. Until a feature moves, the old system keeps serving it and keeps taking business features and fixes.

11. **Only the owner changes the rules (2026-11-11).** `.github/CODEOWNERS` gives the owner `AGENTS.md`, `CLAUDE.md` and `.github/`, the files that say how agents work and what the check and deploys run. Every other file, `package.json`, `README.md`, `docs/`, `scripts/` and `schema/` included, is merged by agents as usual. The ruleset requires code-owner review, so a pull request that changes an owned file cannot merge by itself. The old system grew because any agent could add a rule, a gate or a workflow while doing something else. Here that takes the owner's click. Agents and the owner share one GitHub login today, so no one can approve such a pull request, and the owner merges it with a bypass from the pull request page. A bypass also skips the check. A separate login for agents would make this a normal approval.
